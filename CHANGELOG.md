# Changelog

## v2.5.47

- FIX (bug #106): **the response selector is now validated on its *content*, not just on the element existing — a partially matched container can no longer swallow the tool call.** In the 7 Oct 2026 Qwen test (17:20) the AI finder picked `div.chat-response-message` for `qwen.response`; the v2.5.41 validation passed it (the element exists, is visible and sits low on the page) but the reader only ever got **67 characters** out of it → *no valid tool call*, while in the browser the reply was complete (`ACTION: write_files` + 5 files). Cause: the AI finder could not tell a fragment (a paragraph, or the reasoning block) from the container holding the whole reply, because nothing measured what the selector actually reads. `src/ai-selector-finder.ts` gained a content validation that runs **the real reader** (`getLastResponseText`, so the reasoning blocks and the sidebar are excluded exactly as at run time — bugs #105/#37) over every candidate, with four rules: **1) length** — a proposed response selector must return more than `RESPONSE_MIN_CHARS` (200) characters of real text, otherwise it is rejected with `[ai-finder] response selector rejected: only N chars (need >200)` and the analysis is retried with a prompt that now explains what the response slot must be (a new `ATTEMPT n OF 3` block for `response`: *"the container of the latest assistant reply — reading it must give the FULL reply text …, not a fragment and not the inner 'thinking' block"*, while the input-specific wording is only added when `input` is missing) — with one deliberate exception so that genuinely short replies keep working: when the proposal passed the structural checks, loses no tool call and nothing else in the page reads meaningfully more text, a ≤200-character reply is accepted as-is (`response selector accepted as-is (short reply, N chars)`), but only in the reactive pass, where the sent message proves a reply exists; **2) tool calls** — the last tool-call block in the DOM (`ACTION:` / `TOOL:` / a code fence / `---FILE---`) is located in-page: if it is *newer* than what the selector reads (a variant of the selector that stops before it, or a container the reader cannot see into) the selector is rejected with `[ai-finder] response selector missed tool call markers`; a marker from an **older** message is ignored, so a stale code fence in the history can never reject a correct selector; **3) parent upgrade** — when the proposed selector yields too little, its ancestors (up to 3, built as stable selectors: `#id`, `data-*`, `aria-label`, `tag.class`) are measured and the first one holding **more than 2× the text** is used instead, logged as `[ai-finder] response selector upgraded to parent: <selector>` — this is what rescues both the Qwen thinking block (0 read chars) and a fragment that stops before the tool call; **4) generic fallback** — if nothing usable is found, `[data-message-author-role="assistant"]` is tried first, then the last big text block of the page, climbed with the same 2× rule up to its message container and logged as `[ai-finder] response selector fallback: <selector>`. Two safety rules keep the new leniency from inventing selectors: the generic fallback is only used when we know a message was just sent (the sent text anchors "new text", so welcome-screen or older-reply chrome is never learned) and it is never used for the **proactive** discovery on connect; and when there is *no reply in the DOM at all* (empty chat, welcome screen) the response slot is **deferred** instead of guessed — `findSelectorsWithAI()` drops it from the prompt (logging `no reply in the DOM yet — deferring the response selector`) unless the caller already proved reply content exists, and the retry loop stops early instead of burning three 120 s analyses on a page with nothing to measure. Two adjacent fixes were needed to make the rules usable in real conversations: the response slot now tolerates up to `RESPONSE_MAX_MATCHES` (500) matches — a *correct* selector matches hundreds of nodes in a long chat (`[data-message-author-role="assistant"]` is ChatGPT's own static primary), the real gate being the content — and a structurally rejected proposal is still measured, so the 2× parent rule has a baseline (without it any parent looked "richer" and a bare `div` was upgraded into a valid-looking selector). Selectors that cannot be stored at all (too generic, `learn()`'s own rule, now exported as `isUsableSelector`) are refused here too, so a logged "validated" always means "saved". `NAV_SELECTORS` is exported from `src/selectors.ts` for the in-page probe (one source of truth); the README documents the new behaviour under `freekit.aiSelectorFinder`. Verified with 45 assertions against the compiled `out/*.js` in real Chromium pages (Playwright): the Qwen thinking block upgraded to the full reply container (the tool call with all 5 files is read) and the 48-char fragment that missed the markers upgraded as well, with the `upgraded to parent` / `missed tool call markers` / `rejected: only N chars` lines in the log; a lone fragment rejected without retry while a fragment next to a promo card still retries; a genuinely short reply (≤200 chars) accepted only in the reactive pass and refused in the proactive one, while a fragment next to a tool call is still upgraded instead of accepted; an empty chat rejected with `retryable: false` and no bogus fallback; correct ChatGPT (`[data-message-author-role="assistant"]`, `div.markdown`), Claude, Gemini and DeepSeek selectors accepted **unchanged** (`source: "ai"`); the attribute fallback rescued a bogus proposal and a `null` one; the generic fallback picked the last new big block only in the reactive pass and never on a request without the sent-message anchor; the user's own bubble was never adopted and the accepted text never contained the echo; a stale code fence from an older message did not reject the newest reply; a 400-message conversation accepted a broad selector, read `Message 399` (the *last* reply) and stayed under 30 s, and a bare `div` was refused; `validateSelectors()` kept input/newChat behaviour (ChatGPT/DeepSeek response selectors untouched) and dropped only the unvalidated response. `npm run compile` clean.

## v2.5.46

- FIX (bug #105): **the answer reader no longer mistakes the "thinking" block for the reply — a correctly sent tool call is no longer lost.** In the 7 Oct 2026 Qwen test (17:06) Qwen sent the tool call correctly (`ACTION: write_files`, 5 files), but Freekit read only 93 characters (`"Thinking completed"`) → *no valid tool call*. Cause: the `qwen.response` selector discovered by the AI finder (learned overrides are pushed to the front of the candidate list) matches the **reasoning block**, and the reader returned the first selector's match without ever looking at the reply — the same risk exists for DeepSeek/Claude/Gemini/Kimi, which also render reasoning separately. The read primitive in `src/selectors.ts` (now the single in-page `scanResponses`, used by both `getLastResponseText`/`getLastResponseRead` and `countAssistantResponses`, so the sentinels in `sendAndWait` stay consistent) gained three generic rules: **1) thinking is not an answer** — elements marked as reasoning (`class`/`id`/`data-testid`/`data-role`/`aria-label` containing `thinking|reason|thought`) and short marker texts (`"Thinking"`, `"Thinking completed"`, `"Thought for 12s"`, `"Reasoning"`, `"Se gândește"`, `"Raționament"`, ≤160 chars, anchored at the start) are skipped, and the skipped characters are reported so the reason is visible in the log; **2) containers are split** — if the matched element wraps both blocks, every child block that is not reasoning is kept and concatenated (a plain multi-paragraph reply with no reasoning children is returned byte-identical to v2.5.45), and a leading `"Thinking completed\n\n<reply>"` header is stripped; **3) no dead ends** — if a selector only matches reasoning, the next selector is tried, then the rescue pass prefers real content found by the generic scan over the reasoning text left on screen, and only as a last resort (parity with v2.5.45, so we never answer "empty" where the previous version read something) does it re-read without the attribute filter — the text markers stay filtered in every pass. The count of assistant responses uses the same rules, so the "a new reply appeared" sentinel is not triggered by a reasoning block appearing (which would have returned the *previous* answer as stable). `sendAndWait` (`src/providers/base.ts`) now reads through a single `readResponse()` helper that logs `[read] response: N chars (thinking: M chars ignored)` whenever the outcome changes. Verified with 30 assertions against the compiled `out/*.js` in real Chromium pages (Playwright): the Qwen case reproduced with v2.5.45's algorithm and fixed by v2.5.46 (the tool call with all 5 files is read; 93 thinking chars reported as ignored) both when the learned selector matches only the reasoning block and when one selector matches the reply *and* the reasoning (reasoning last); Claude extended thinking in a single container (the reply alone is read), DeepSeek `ds-think-content` + `ds-markdown`, Gemini `div.thought` + `model-response`; the `"Thinking completed"` marker is ignored even without any "thinking" class/id; a page whose only content is reasoning still reads something (parity) while the rescue pass prefers the real answer found generically; a normal reply (single node, multi-paragraph container, generic fallback, user+assistant messages, sidebar exclusion — bug #37) is **identical** to v2.5.45, confirmed by a randomized sweep of 60 generated pages × 3 selector sets × (read + fallback + count); counting is identical without reasoning blocks and does not count reasoning blocks, while a new reply still increases the count. `npm run compile` clean.

## v2.5.43

- FIX (bug #99): **`edit_file` no longer fails silently when OLD_TEXT differs only in whitespace/quotes/EOL, and every failure now says exactly what was searched.** In the 7 Oct 2026 Mistral test (14:28–14:30) `edit_file` returned `ok=false` four times and the log said only `old_text not found in <path>`, so there was no way to tell whether the block was truncated, re-indented, re-quoted or sent with other line endings. `src/tools.ts` now matches in a **ladder**: exact (bit-for-bit), then EOL-unified (`\r\n` / `\r` → `\n`), then collapsed horizontal whitespace, then typography (curly quotes `‘ ’ “ ”` → `' "`, en/em dash → `-`, NBSP / narrow NBSP → space), then per-line trim (leading/trailing spaces, plus runs of blank lines folded into one). Every rung normalises the file **and** `old_text` identically and keeps a `normalized index → original index` map (`normalizeWithMap`), so the replacement still lands on the REAL offsets in the file — including a match that ends on a line break, which consumes the whole `\r\n` instead of leaving a stray `\n`; the diff preview, the approval card and the write all use that same range. A tolerant hit is reported to the model as `Edited <path> (tolerant match: <rung>)` and logged as `[tool] edit_file: tolerant match (<rung>) in <path>`. When no rung matches, the failure is no longer mute: the log gets `[tool] edit_file failed: old_text not found in <path> (len=N, first20=<sample>)` (EOL/tab/NBSP escaped in the sample) plus a second line with the nearest match, and the error handed back to the model carries the path, the nearest match with 3 lines of context (`Nearest match, around line N:`) and a hint to re-read the file — the anchor is the longest line of `old_text` that actually exists in the file, so a line the model invented cannot waste the hint. A whitespace-only `old_text` is refused instead of matching at a random offset, and editing a path that does not exist no longer reports `old_text not found` (which sent the model hunting for differences in a missing file) but `File not found: <path>`.

- FIX (bug #100): **the free-plan / quota limit is now detected and reported instead of silently truncating replies.** In the same Mistral test the account was on the free plan, the answers were cut short (so the tool calls arrived incomplete and `edit_file` kept failing) and Freekit said nothing about the real cause. `detectProviderError` (`src/providerErrors.ts`) has a new `plan_limit` kind that fires on the limit phrasings — `free plan`, `quota exceeded`, `limit reached`, `you've reached …`, `daily limit`, `message limit`, `try again later` — and, when the page exposes an upgrade CTA, on `upgrade your` / `upgrade to` / `upgrade now` combined with a limit word; the bare word "upgrade" is deliberately NOT enough on its own, because it would fire on any ordinary answer that happens to mention it next to the always-present sidebar link. `src/providers/base.ts` now also scans the DOM for those CTAs (`scanUpgradeLink`: `a[href*="/upgrade"]`, `a[href*="/plans"]`, `a[href*="/pricing"]`, preferring a visible element) and feeds the absolute URL into the detection — read once per message and memoised — so the card shows the provider's REAL upgrade URL; `upgradeUrlFor()` keeps the known Claude/ChatGPT URLs as the fallback, and the existing `out_of_messages` / `rate_limit` kinds now carry an upgrade link too when the page has one. Detection runs both on the page scan (banner selectors + page tail, as before) and on the reply text read out of the DOM (short replies only, ≤ 500 chars, so a normal answer that merely mentions a limit is not mistaken for a banner). The error travels the existing `provider_error` path, so the chat gets the familiar card — now titled `⚠️ <Provider> — free plan / limit reached` (`media/chat.js`) — with the human message, the reset time when present, the Upgrade link and the Show Browser / Retry / Switch provider buttons. Verified with 50 assertions run against the compiled `out/*.js`: the whole normalisation ladder (CRLF↔LF, 2-vs-4-space indentation, curly quotes, extra indent on OLD_TEXT, blank-line runs, replacement ending on CRLF, whitespace-only and empty OLD_TEXT), the exact failure log/error format, `plan_limit` with and without a DOM link plus regressions for `out_of_messages` / `rate_limit` / `login_required` / `memory_full` / `captcha` / `model_missing` and a normal reply that stays undetected while an upgrade link is present, and `scanUpgradeLink`'s visible-element preference and fallbacks. `npm run compile` clean, `node --check media/chat.js` clean.

- FIX (bug #98): **deleting files/folders is now a first-class tool instead of a shell workaround.** In the same test (13:29:07) the model asked for `delete_file` twice, got `Unknown tool: delete_file` both times, gave up and fell back to `run_command` with `rm` — it worked, but only because the shell accepted an OS-specific command, and it bypassed the workspace-trust, scope and approval guards the write tools have. ## v2.5.41

- FIX (bug #95): **a selector proposed by the AI finder is now strictly validated in the page before it is saved.** In the 7 Oct 2026 ChatGPT test (12:49:02) the finder proposed `input[aria-label="Line wrap"]` for `chatgpt.input` — a hidden helper input, not the composer — and Freekit saved it as a learned override, leaving ChatGPT broken until a manual fix. ## 2.4.8 — 2026-10-05

**The tool-call parser survives real model output** — a reply whose `content` holds nested braces and escaped quotes no longer ends in *"NO TOOL CALL DETECTED"* followed by two useless auto-retries; the tool call is now found inside whatever text surrounds it.

- **`src/toolCallParser.ts`** (new) — replaces the old `parseToolCall` in `chatView.ts`. The old parser first demanded that the *whole* reply be a single JSON object (`!clean.startsWith('{') || !clean.endsWith('}')` → `null`), so any prose or a fence around the JSON meant "no tool call", and its recovery regex `/\{\s*"tool"\s*:[\s\S]*\}/` was greedy at the wrong end. The extractor now scans once, string- and escape-aware, and collects candidates in order: the body of every fenced code block, every **balanced** `{…}` that opens with the `"tool"` key (so nested braces inside `content` and the trailing `}}` no longer break it — spaces and `{'tool':` variants included), the last balanced object in the text, then the whole reply with a leading fence stripped. Each candidate goes through `JSON.parse` and then through two tolerant repairs: real control characters (newline / CR / TAB, which web providers leave unescaped inside `content`) are escaped, and unescaped quotes inside values are re-escaped, keeping the existing quote heuristic but without its `slice().match()` per quote.
- **Clear error instead of raw JSON** — when the reply is plainly a tool-call attempt (starts with `{"tool":`, fence or not) that still cannot be parsed after the two auto-retries, the chat now shows **"Model returned malformed tool call. Try again or switch provider."** and records it in the conversation instead of posting the broken JSON as the final answer.
- **`src/chatView.ts`** — `parseToolCall` delegates to the new module; the now-dead `normalizeToolCall` / `repairJsonQuotes` private methods are removed. Behaviour of the agentic loop (retry policy, step limit, auto-verify) is unchanged.

## 2.1.0 — 2026-10-02

**Hardware tiers + a model catalog that covers any machine** — from a 4 GB laptop to an 8×H100 workstation, the local-model suggestion is now actually right for the hardware.

### Detection (`src/hardware.ts`)

- **Every GPU, not just the first** — `HardwareInfo.gpus` now carries the full list with `vendor` (`nvidia` / `amd` / `apple` / `intel` / `unknown`), `type` (`consumer` / `workstation` / `server` / `igpu`) and `bandwidthGbps`. Classification is name-driven (Quadro / RTX A / Radeon Pro → workstation, Tesla / Instinct / A100 / H100 → server, Intel UHD / Iris / Radeon Graphics / Apple M → iGPU), and the workstation pattern uses `\b` after the exact model so an RTX 4060 is not mistaken for an RTX 4000.
- **Real memory bandwidth** — `nvidia-smi --query-gpu=...,memory.bus_width,clocks.max.memory` gives `bus width × clock × 2 / 8` (an RTX 4090 reports ~1008 GB/s). Apple Silicon gets its published bandwidth per chip family (M1 → M4 Max), because unified memory bandwidth is what decides speed there. Drivers that do not expose `clocks.max.memory` fall back to the old two-field query.
- **`totalVramGb`** — the sum over *discrete* GPUs only; iGPUs share system RAM, so counting their reported adapter memory would double-count. **`unifiedMemoryGb`** (~70% of RAM) is set for Apple Silicon, where the model has to fit in that one pool instead of VRAM + RAM.
- **Machine tier `T0`-`T6`** — `tier` is derived from the model memory budget (`max(unified, totalVram + 0.7 × RAM)`) with thresholds 4 / 12 / 24 / 48 / 96 / 192 GB. `minTierFor()` maps a model's memory back to the tier where it runs comfortably, and `tierTarget()` gives the human-readable "what can this machine run" line. Both directions use the same table, so they cannot drift.
- **Free disk** — `freeDiskGb` via `fs.statfs` on the Ollama models directory (honours `OLLAMA_MODELS`), walking up to the nearest existing path and falling back to `df -Pk`. `0` means unknown.
- **VM detection** — `isVM` from `systemd-detect-virt` / DMI on Linux, `kern.hv_vmm_present` + `hw.model` on macOS, `Win32_ComputerSystem`/`Win32_BIOS` on Windows, plus a free CPU-model check on every platform. Best-effort: a failed probe never blocks detection.

### Recommendations

- **Catalog grew from 10 to 51 models** — `qwen2.5-coder:0.5b` up to `deepseek-r1:671b` / `qwen3-coder:480b` / `llama4:maverick`. Every `needGb` was checked against the real Ollama registry manifests (blob size + KV/context headroom) instead of being estimated, and every id was verified to exist in the Ollama library.
- **Speed-aware scoring** — a model is `fast` when it fits entirely in VRAM (or unified memory), `medium` when it is an MoE with ≤10B active parameters that runs partly on the CPU (gpt-oss:20b on 32 GB RAM), and `slow` when a dense model is pushed into RAM. Ordering is speed first, quality second, so a machine is no longer told to download a 30B that only fits across CPU and GPU while a fully GPU-resident option exists.
- **One pick per size class** — the list mixes the best overall, a different size class and a smaller option, so you get three genuinely different choices instead of three near-identical models. Models that do not fit on the free disk space are skipped (unless that would leave nothing).
- **Recommendations carry `speed`, `tags` (`code` / `reasoning` / `vision` / `general` / `moe`) and `minTier`**, and the model menu labels installed models `recommended · GPU` / `recommended · CPU-friendly` / `recommended · CPU (slow)` via the new `modelSpeed()`. The hardware footer line now ends with the tier, and its tooltip lists every GPU with type and bandwidth, unified memory, free disk, VM status and the recommendations.
- **Status report** — `hardwareReport()` replaces the two ad-hoc lines: tier + target, CPU, usable memory, one line per GPU, total VRAM, unified memory, disk and environment.

> **Note:** the existing `ramGb` field kept its name (it is what `hardwareSummary` and the webview payload already used) — there is no `totalRamGb`.

## 1.10.0 — 2026-10-02

- **Semantic code search (`search_semantic`)** — the AI can now find code by **meaning** instead of exact text: ask *"where do we validate the login token?"* and it gets the closest snippets back, each with `path:startLine-endLine`, a cosine-similarity score and the code itself. - **Hardened message↔checkpoint wiring** — the user-message id is attached to the chat bubble directly in `add()` (one single code path), and restore buttons are re-attached after every user message, so the 🔄 button can no longer miss its checkpoint because of message ordering (e.g. right after a webview reload).
- **Text-to-speech for AI replies** — every assistant message gets a 🔊 button (next to Copy) that reads the answer aloud via the Web Speech API, with a Romanian voice when one is installed (`ro-RO`). Long answers are split into sentence-sized chunks so speech engines don't cut them off, and markdown (code blocks, links, emphasis) is stripped first. Click the button again to stop; reading also stops when you clear the chat or send a new message.

## 0.9.5 — 2026-10-01
